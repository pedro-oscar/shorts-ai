# Remotion por projeto, com `node_modules` compartilhado

Cada projeto tem a própria pasta `remotion/`, com `src/` e `public/` copiados do template ao criar o projeto. As dependências do Node (`node_modules`, 300–600 MB) ficam numa cópia única nos dados do app, ligada por symlink no Linux e no macOS e por junction no Windows, que não exige administrador. Uma cena criada pelo Claude só existe no projeto que a criou. Assim ela não invalida o cache de render dos outros projetos, e vários vídeos podem renderizar em paralelo sem trava no Remotion.

## Consequences

- Cenas não são reaproveitadas entre projetos.
- Confirmado no Linux (Node 22, Remotion 4.0.533, ticket 08): com o `node_modules` ligado por symlink, `tsc` e `remotion still` empacotam e renderizam o template. O webpack segue o caminho real e a pasta precisa se chamar literalmente `node_modules`. Confirmado também no Windows 11 (Node 24, ticket 19): com o `node_modules` ligado por junction, `tsc`, `remotion still` e as cenas do `shorts-cli` empacotam e renderizam o template.
- O cache do webpack (`node_modules/.cache/webpack`) e o Chrome do Remotion (`node_modules/.remotion`) caem na pasta compartilhada; com projetos empacotando em paralelo, o cache precisa ser desligado ou separado por projeto. O template desliga o cache (`Config.setCachingEnabled(false)`): com ele desligado, nada cai em `node_modules/.cache`. O Chrome do Remotion continua em `node_modules/.remotion`, único e só de leitura entre uma instalação das dependências e a seguinte.
- O `node_modules` compartilhado segue o template da versão instalada do app (ticket 49). Quando uma atualização muda o `package-lock.json` do template, a Preparação mostra as dependências do Remotion como faltando e roda o `npm ci` de novo; o Chrome headless, que vai embora com o `node_modules`, é baixado outra vez. A Preparação abre antes de qualquer render, então nenhum projeto empacota enquanto o `node_modules` é trocado. Os projetos criados antes da atualização guardam o `src/` deles e passam a usar as dependências novas. Por isso uma mudança de dependências do template precisa manter o `src/` das versões anteriores empacotando: acrescentar pacotes ou subir versões compatíveis. Remover um pacote ou subir para uma versão incompatível quebra o render dos projetos antigos. O hash do pacote cobre também as dependências instaladas, pelo `node_modules/.package-lock.json` que o `npm` grava (ticket 50): a próxima produção de um projeto antigo o empacota de novo, e nenhum pacote feito com as dependências de antes roda com o `@remotion/renderer` novo. Os reels prontos ficam como estão, porque a troca não entra no código comum de que cada reel depende; assim uma atualização não renderiza de novo todos os reels de cada projeto antigo. Se a versão nova do Remotion ou das fontes mudar a imagem, só os reels renderizados depois da troca saem com ela. Um `node_modules` por versão do template evitaria tudo isso, mas custaria 300–600 MB a cada versão.
- O empacotamento (`bundle()`) roda uma vez por projeto, depois de o Claude mexer nas cenas, e cada reel é renderizado desse pacote com `renderMedia()`, em vez de um `npx remotion render` por reel, que empacota de novo a cada vez.
- O render de um reel depende do código comum do Remotion do projeto e só das cenas que ele cita (ticket 41). O pacote depende de tudo. A convenção nome = arquivo faz a ligação: a cena `X` de um motion é `src/scenes/X.tsx`, como o motion-guide manda. O registro (`src/scenes/index.ts`), que muda a cada cena criada, fica fora. Uma cena citada sem esse arquivo faz o reel depender de toda a pasta `src/scenes/`. Os outros arquivos da pasta (`types.ts`, helpers) são código comum. Três casos passam sem refazer o reel, e esse risco foi aceito: uma cena que importa outra, um remapeamento no registro (`Grafico: OutroComponente`) e efeitos colaterais de uma cena no nível do módulo.
